1. 导言

1.1 编写目的

本《项目需求分析规格说明书》（Software Requirements Specification，简称 SRS）旨在全面、准确、无歧义地定义三峡大学《实验室设备管理系统》（LabMS v1.0）的功能性需求、非功能性需求、运行环境、角色用例模型及外部实现约束。本文档经需求提出方与第 01 组全体研发成员共同评审确认，是后续开展系统体系结构设计、数据库建模、核心业务代码实现、高保真交互原型验收以及黑盒/白盒测试的唯一需求基线依据。

1.2 项目范围

本项目围绕高校教学与科研实验室的固定资产设备及低值易耗品全生命周期管理展开。系统命名为《实验室设备管理系统》（LabMS），划分为“公共与师生服务子系统”和“实验室与后台管理子系统”两大业务域，覆盖用户认证与 RBAC 权限管理（M1）、设备信息与状态机管理（M2）、设备采购与自动批量入库（M3）、设备借用与受损归还自动转修（M4）、设备维修闭环与报废核销（M5）、仓库库存盘点与完好率统计（M6）、实验耗材出入库与低水位预警（M7）七大核心模块。

2. 项目介绍

2.1 项目背景

在高校实验教学中心日常运转中，电工电子实验室、人工智能实验室、嵌入式系统实验室等场馆存放着大量不同档次与用途的教学科研设备。长期以来，实验室管理面临“重采购、轻流转、弱盘点”的信息化短板：一方面，学生在课程设计与学科竞赛期间频繁借用开发箱、示波器等设备，手工台账无法实时反映某台设备是否已在库、是否处于故障待修状态，常导致借用冲突；另一方面，设备在归还验收时若发现硬件损坏，纸质登记往往未能及时转化为维修工单，致使带病设备再次流向实验课堂；此外，危化试剂（如无水乙醇）与常规耗材（如无铅焊锡丝）缺乏库存红线自动监控，存在断供或超领隐患。因此，亟需构建一套覆盖“申购—入库—借还—维修—报废—盘点—耗材预警”的现代化实验室设备管理系统。

2.2 项目目标

（1）业务全链路闭环目标：消除人工二次录入断层，实现采购申请审批通过并验收入库后 100% 自动批量生成在库（IN_STOCK）设备台账；实现借用设备受损归还（conditionOk = false）时 100% 自动流转至维修态（MAINTENANCE）并自动派发待处理维修工单。

（2）状态强约束防错目标：通过有限状态机严格管控设备四态转换，彻底杜绝“重复借出已借设备”、“借出维修中/已报废设备”、“未归还直接报废”以及“已报废终态设备逆向复活”等违规操作。

（3）实时盘点与预警目标：支持一键生成全院实验室库存统计大盘（总台数、各状态计数、固定资产总值、设备完好率），并对低于安全阈值的实验耗材实现 100% 实时识别与高亮预警。

4. 功能规格

4.1 系统角色（Actor）分析

本系统依据最小权限原则（Principle of Least Privilege）构建四级 RBAC 角色体系，定义在枚举类 cn.edu.ctgu.labms.domain.Role 中。四类系统角色（Actor）及其业务权限边界分析如下，系统角色与功能权限矩阵如表 4-1 所示。

（1）学生（STUDENT）：系统的基础服务使用者。可注册登录、多维检索实验设备台账、申请借用在库设备、归还所借设备、对发现故障的设备提报维修申请，以及按课程实验需求领用常规实验耗材；严禁执行设备建档、提交新设备采购单、审批工单或批准报废。

（2）指导教师（TEACHER）：继承学生的查询、借用、报修与耗材领用能力，同时具备发起新设备采购申请单（submitPurchaseOrder）及作为课程指导教师协助审核借用流程的业务权限；但无权直接批准国有固定资产报废或管理系统账号。

（3）实验室管理员（LAB_MANAGER）：实验室日常运维的核心执行者。负责登记新设备台账与库位调拨、审批采购单并执行到货批量入库、审批借出申请与归还完好性验收、处理维修工单并确认完工恢复在库、提报或审批设备报废、执行耗材建档与补货入库、查看仓库完好率盘点大盘。

（4）系统管理员（ADMIN）：系统最高安全与资产监管角色。除拥有实验室业务审批与报废核准权限外，独家拥有用户账号启用/禁用控制（setUserActiveStatus，含防自锁保护）、用户角色变更授权（changeUserRole）以及全院安全审计日志检索审查（getAuditLogs）权限。

4.3 师生服务子系统功能需求

公共与师生服务子系统面向全体学生与指导教师提供 7 项核心业务用例（UC01～UC07）：

（1）用户注册与登录认证（UC01）：支持输入用户名、明文密码、真实姓名、角色与所属院系完成注册，系统强制采用 SHA-256 哈希算法存储 64 位十六进制密码摘要；登录时校验账号存在性、启用状态（active == true）与密码摘要匹配性，并写入审计日志。其详细用例规约如表 4-2 所示。

（2）多维检索设备台账与状态（UC02）：支持按关键字（匹配设备编码、名称或型号规格）、设备分类（如电子测量仪器、计算服务器、嵌入式教学设备）、实时状态（IN_STOCK 等四态）及存放位置进行任意组合模糊或精确查询。

（3）提交设备借用申请（UC03）：借用人选择目标设备并填写借用用途、借出日期与应还日期，系统强制校验应还日期不早于借出日期，且设备当前状态必须为“在库可用（IN_STOCK）”。其详细用例规约如表 4-3 所示。

（4）归还设备与完好性登记（UC04）、提报设备故障报修（UC05）、提交新设备采购申请（UC06，仅教师与管理员）以及申领实验试剂与耗材（UC07）。其中实验耗材领用出库的详细用例规约如表 4-4 所示。

规约属性 内容说明 规约属性 内容说明
用例编号 UC01（对应服务：AuthService） 用例名称 用户注册、登录认证与RBAC鉴权
主要参与者 学生、教师、实验室管理员、系统管理员 优先级 高（P0 基础安全底座）
前置条件 系统服务已启动；若执行登录，用户账号须已完成注册。
基本事件流 1. 用户输入用户名与登录密码提交认证请求；

用例编号 UC03（对应服务：BorrowService） 用例名称 提交设备借用申请与借出审批
主要参与者 借用人（学生/教师）、审批人（实验员） 优先级 高（P0 核心流转业务）

E2. 设备处于 BORROWED、MAINTENANCE 或 SCRAPPED 状态：抛出 IllegalStateException 拒绝重复借出或带病借出。
后置条件 设备状态变更为“已借出（BORROWED）”，进入借用期及超期监控队列。

规约属性 内容说明 规约属性 内容说明
用例编号 UC07（对应服务：ConsumableService） 用例名称 申领实验试剂与耗材出库
主要参与者 指导教师、学生、实验室管理员 优先级 中（P1 物资管控业务）

2. 系统校验当前库存满足 currentStock >= quantity；
3. 系统扣减库存：newStock = currentStock - quantity 并保存；
4. 系统自动检测扣减后是否满足低水位条件 newStock < safetyThreshold，若触发则在审计日志中附加 【触发低库存预警】 标记并纳入预警清单。
异常/扩展流 E1. 领用数量 $\le 0$：抛出 IllegalArgumentException("领用出库数量必须大于0")；
E2. 申请领用数量超过当前实际库存（currentStock < quantity）：抛出 IllegalStateException("耗材库存不足") 拦截超领。
后置条件 耗材库存准确扣减；若跌破安全阈值，该耗材自动出现在 getLowStockWarnings() 预警看板中。

4.4 实验室与后台管理子系统功能需求

实验室与后台管理子系统面向实验室管理员与系统管理员提供 9 项核心管控用例（UC08～UC16）：

（1）设备建档与生命周期维护（UC08）：支持实验员录入设备编码、名称、规格、分类、厂商、单价、购置日、质保到期日及存放位置，强制校验编码唯一性、单价非负性及质保期不早于购置日，初始状态设为 IN_STOCK。

（2）设备采购审批与到货自动批量建账（UC14）：管理员对处于 PENDING 状态的申购单进行合规审批；批准通过并执行到货验收时，系统按申购数量 quantity 循环自动调用设备建档服务，批量生成连续编号的 IN_STOCK 设备台账，并将申购单状态置为 COMPLETED。其详细用例规约如表 4-5 所示。

（3）设备归还验收与受损自动转修联动（UC04/UC09/UC10）：管理员验收归还设备时，若选择“完好（conditionOk = true）”，设备状态恢复为 IN_STOCK；若选择“受损（conditionOk = false）”并填写故障现象，系统自动调用 MaintenanceScrapService.reportFault()，将设备状态切换为 MAINTENANCE 并自动生成待处理维修工单。其详细用例规约如表 4-6 所示。

（4）设备报废核销与永久终态锁定（UC11）：针对无法修复或超期服役的在库/维修中设备，经管理员批准报废后，系统自动将该设备关联的所有未结案维修工单同步结案，并将设备状态永久锁定为终态 SCRAPPED。其详细用例规约如表 4-7 所示。

3. 系统扫描该设备关联的所有历史工单，若存在未结案（PENDING）的维修工单，自动将其同步结案并标注“无法修复，已转报废流程处理”；
4. 系统驱动状态机将设备变更为永久终态 SCRAPPED，生成报废单（如 SC-2026-303）并记录审计日志。
异常/扩展流 E1. 学生或普通指导教师尝试批准报废：被 RBAC 拦截并抛出 SecurityException；
E2. 尝试将已处于 SCRAPPED 终态的设备再次借出、维修或恢复在库：状态机返回 false 并抛出 IllegalStateException。
后置条件 设备永久锁定为 SCRAPPED 终态，在盘点统计中自动从完好率分子中剔除。

4.5 非功能性需求

4.5.1 界面需求

系统前端与高保真交互原型（prototype/html/index.html）采用清爽现代的高校智慧实验室视觉规范（主色调深海蓝 #1F4E79 搭配活力蓝 #2B6CB0）。设备四态采用高辨识度语义色彩徽章区分：在库可用采用翠绿色（#16A34A）、已借出采用琥珀色（#D97706）、维修中采用紫色（#7C3AED）、已报废采用警示红色（#DC2626）。工作台采用左侧固定导航栏 + 顶部角色切换与安全状态栏 + 右侧数据卡片与交互弹窗的经典 B/S 管理后台布局。

4.5.2 响应时间需求

在校园网常规负载下，系统各核心业务的响应时间须满足以下性能指标：① 用户登录认证与 SHA-256 哈希校验响应时间 $\le 50\text{ ms}$；② 多维组合条件检索设备台账（支持按关键字、分类、状态、库位过滤）响应时间 $\le 100\text{ ms}$；③ 采购单审批并批量生成 10 台以内设备台账事务响应时间 $\le 150\text{ ms}$；④ 仓库库存盘点与完好率统计汇总计算响应时间 $\le 100\text{ ms}$。

4.5.3 可靠性需求

系统必须具备严格的防御式编程与边界容错能力：① 状态机 100% 防错：任何违反四态迁移图的操作均在内存状态变更前被拦截，不产生脏数据；② 空仓库零除保护：当新建实验室设备总数为 0 时，完好率计算公式自动返回默认 100.00%，严禁触发 ArithmeticException 或 NaN；③ 防重复提交：已审批的采购单、已归还的借用记录、已完工的维修单均具备幂等锁保护，防止重复点击造成库存错乱。

4.5.4 可扩展性需求

系统遵循开闭原则（OCP）与依赖倒置原则（DIP），采用五层解耦架构设计。业务逻辑层（service）与数据访问层（dao）职责分离，当前内置的 InMemoryDatabase 内存事务容器可无缝替换为基于 JDBC / MyBatis 的 MySQL 8.0 持久化实现，而无需修改上层业务规则与状态机代码。

4.5.5 系统安全性需求

（1）凭证不可逆加密：严禁明文存储用户密码，全部密码均通过 MessageDigest.getInstance("SHA-256") 转换为 64 位十六进制哈希串存储。

（2）细粒度 RBAC 鉴权与防自锁：所有写操作均强制调用 authService.requireRole()；管理员禁用账号接口内置自检逻辑（adminId.equals(targetUserId) 时抛出异常），防止系统管理员误禁用自身导致系统锁死。

（3）全链路安全审计可追溯：所有登录、越权拦截、建档、采购审批、借出、归还、报修、报废、耗材出入库操作均自动生成带精确时间戳与操作人 ID 的 AuditLog 记录，支持按操作人追踪审计。
